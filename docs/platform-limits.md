# GeWe 平台限制与封号红线

> **来源**：GeWe 官方「[风险说明](https://doc.geweapi.com/doc-6356339)」与「[调试指南](https://doc.geweapi.com/doc-3146245)」（抓取 2026-09-11）。
> **性质**：外部平台的硬约束与经验值。**改动回复管道（尤其限速、并发、多账号）前必读。**
> 官方原文：[风险说明](https://doc.geweapi.com/doc-6356339)、[调试指南](https://doc.geweapi.com/doc-3146245)。

## 0. 一句话

**风控判的是「像不像真人」，不是「发了多少条」**——官方原文：「业务风控系统用正常人的方式来判断一个号是否是真人，不是真人操作且运行在非官方环境的，账号最终一律封杀掉，一个不留」。所以速率只是其中一环；**多设备、充电状态、位置不动、内容同质化**同样会被判定。

---

## 1. 速率是两条约束，不是一条（⚠️ 修正我们的旧结论）

官方给了**两个不同维度**的上限，我们此前的文档**只写了第一条**，这是实质遗漏：

| 维度 | 官方口径 | 出处 |
|------|----------|------|
| **总量** | 「每分钟不超过 **40 条**」；「每条消息处理约 1–2 秒，每分钟建议处理 **20–40 条**」 | 调试指南 / FAQ |
| **不同好友数** | 「同个时间段内频繁给多位好友发送消息，**即便是正常的聊天内容**，也会被限制聊天功能」；「**1 分钟超过 10–15 位好友**就会有风险」 | 风险说明 §03.8 |

**第二条才是我们的真正约束。** 原因：自动回复是**一条一条发给不同好友**的（同一好友连发多条会经 debounce 合并成一次回复），所以「条数/分钟」≈「不同好友数/分钟」。

也就是说 —— **若按 40 条/分钟跑，我们对的是 40 位不同好友/分钟，是官方风险线的 2.7 倍。** 40 只是"绝对不超"的硬顶，不是安全运行点。

### 落地要求

- 新增**不同好友数**限流：`SEND_MAX_DISTINCT_FRIENDS_PER_MINUTE`，**建议 10**，生产初跑 6–8。
- 目标级间隔相应放宽：**不同好友 `U(4, 8)s`**（均值 6s ≈ 10/分钟），让间隔本身就把速率压在安全线内，而不是让限流器长期排队。
- `SEND_MAX_PER_MINUTE=40` 保留为**硬顶兜底**，只防突发，不作为目标速率。
- 单好友间隔官方口径是「≥1 秒」；我们沿用更保守的 `U(1.5, 3.5)s`。
- 群消息官方建议「随机 2~5 秒」——P0 不做群，P3 再说。

**官方三条硬要求（我们已满足，勿改）**：必须用**队列**发送、**禁止并发**、控制间隔。

## 2. 静默降权：发送成功 ≠ 对方看得见

这是最隐蔽的一类故障，官方明确存在，但**不会返回错误**：

| 现象 | 官方解释 |
|------|----------|
| 群消息发出去了，但群里只有部分人能看到 | 内容同质化、营销感强、发送频率过高，**微信会降权分发** |
| 朋友圈发出去只有自己可见 | 微信「**选择性可见机制**」；原因含频率过高、敏感词、图片违规 |
| 消息接收延迟 | 「微信会对高频操作**降低分发优先级**」 |

对我们的影响：

- `postText` 返回 `ret:200` **只代表接口调用成功，不代表已送达/可见**。
- 因此 §「发送成功」的判定是**接口语义**；真正的送达无法确认。这也是「超时只重试一次」之外，另一个不能依赖"发送成功"做业务承诺的理由。
- **减少同质化**：回复内容不要模板化重复（system prompt 里避免固定句式输出）。这是产品层要求，不只是技术层的。

## 3. 养号窗口与安全环境（多账号/上线后必守）

**"安全环境"的官方定义：登录满 48 小时。登录未满 48 小时属非安全环境，不得使用敏感接口。**

| 阶段 | 官方要求 |
|------|----------|
| 新注册号 | **2 个月内不做任何营销动作**；先完善头像/昵称/签名/朋友圈，绑定越多越好 |
| 新接入号 | 「新账号先在线 **3–5 天**，养号后再做高频操作」 |
| 重新登录后 | 登录未满 **48 小时** = 非安全环境，避免敏感操作与高频发送 |
| 新账号前 24 小时 | **掉线属正常现象**，用上次 appId 重新扫码即恢复稳定（一般可在线 3 个月） |
| 群二维码 | 需在线 3 天 |
| 朋友圈 | 需在线 1 天 |
| 添加好友 | 新登录账号需在线 3 天后再调用，否则对方收不到验证 |

**对我们（P0 只有自动回复）的落地建议**：

- 记录每个执行节点的**首次成功登录时间**；距登录 **< 48 小时**时自动降速（如降到日常的 1/3）。
- 官方入口已警告：「**新注册账号、未实名认证账号或曾被封禁的账号**，均属低质量账号，不建议接入本平台」。**接入前先人工确认账号质量**，不要用新号/买的号直接上自动化。

## 4. 账号与部署层红线（代码管不到，运维必须知道）

以下都出自官方「常见风控 / 高概率风控」，**与发送逻辑无关但同样封号**：

| 红线 | 官方描述 |
|------|----------|
| **24 小时充电** | 「一天 24 小时充电状态的手机上的号，系统会判断是营销号」 |
| **位置长期不动** | 「一个手机上的号，老待在一个地方不动，不移动，就是营销号」 |
| **同 WiFi 批量养号** | 「一旦被系统检测到，批量封号」→ 建议插卡手机用干净 IP |
| **频繁切设备/切号** | 「同个设备频繁更换账号登录，或同个账号频繁在多个设备登陆…有封号风险」 |
| **多开数量过多** | 「安装多开数量过多。（所以无限多开实则是坑）」 |
| **同区域批量注册** | 「同个区域批量注册新号（5 个以上）…封号」 |
| **连号段手机卡** | 「同时批量注册新账号，必封」 |
| **加违规群** | 红包群/清货群/推股群 → 被判赌博号、营销号 |
| **被投诉** | 「账号被投诉」属常见封号原因 |
| **长期不登录** | 「长时间未登录」 |
| **频繁转账/红包** | 24h 内红包超 100 次限制社交功能，**超 200 次必封** |

**多账号部署最低要求**：**账号维度完全隔离**——独立设备/IP、独立 appId、独立配置（§7）；**不要把多个号跑在同一台 24 小时插电、位置不动的机器上**。

## 5. 敏感接口：P0 一律不碰

官方点名 **「添加好友 / 同意好友 / 群二维码 / 创建群聊」** 为敏感接口，**使用不当会直接触发风控**，且必须在安全环境（登录满 48h）下用。

官方「高风险行为」明令禁止：**异地添加好友、高频群发、自动通过好友、内容违规**。

**P0 的范围只有「收私聊 → 回私聊」，不涉及以上任何接口**。掉线重登是人在 GeWe 控制台做的登录类操作，本服务不代劳；若运营去重登，必须复用 `appId`，并受§3 的 48 小时窗口约束。

## 6. 媒体接收（图片已落地；语音/视频待做）

> **状态（2026-09-13）**：图片接收**已实现**。落点：`media` 表 + `app/services/media.py` + worker 下载循环；
> 媒体**不落自有存储**（直接用 GeWe 换来的公网 URL 喂模型），历史里只有 `[图片]` 占位。
> 语音/视频仍未做，但表结构（`media_type` + `source` + `asset_ref`/`text_repr`）已留好位置。

图片/语音/视频的**接收**链路有独立且容易踩的约束：

### 接收链路：回调只给 XML，媒体要另调下载接口

回调里 `msgType=IMAGE/VOICE/VIDEO/FILE` 时，`content` 是 **XML**，**不含可直接用的文件**。必须再用 XML 调下载接口换 `fileUrl`：

| 类型 | 接口 | 必需参数 | 备注 |
|------|------|----------|------|
| 图片 | `/gewe/v2/api/message/downloadImage` | `appId`、`xml`、**`type`**（1 高清 / 2 常规 / 3 缩略图） | 失败时**换另一种质量重试**；不是所有图都有高清版 |
| 语音 | `/gewe/v2/api/message/downloadVoice` | `appId`、`xml`、**`msgId`** | 返回 **silk 格式**，需转 mp3（官方给 `silk-v3-decoder`） |
| 视频 | `/gewe/v2/api/message/downloadVideo` | `appId`、`xml` | |
| 文件 | — | — | 官方：「**需使用第二条回调下载**」（机制特殊，P2 再研） |

### 三条硬约束

1. **`fileUrl` 仅 7 天有效**（且是 **GeWe 的签名 TTL**，不是微信资源的寿命；我们无法续签）→ 想在 7 天后回看就必须落自有存储。**本项目已决策不落盘**，代价是历史图片永远只有 `[图片]` 占位。
2. **下载必须串行队列 + 限速**：「必须使用下载队列串行处理」「每条下载间隔 **3~10 秒**」「同一消息只下载一次」；「下载频率过高，**严重时甚至掉线**」。
3. **下载是独立于发送的限速域** → 已实现为**独立的下载循环**（账号内串行、账号间并行），不复用发送令牌桶。三层控制：账号内间隔 3~10s（`media.DOWNLOAD_INTERVAL_SECONDS`，**安全底线，不可放宽**）、账号日配额、账号 pending 积压上限（超限标 `skipped` 走失败文案）。常量都在 `app/services/media.py`，不进 env。
   > **只有第 1 步（调 `downloadImage` 换 URL）消耗账号会话**，所以限速加在这里；第 2 步（CDN GET 图片字节）是**百炼服务器**在做，与我们账号无关，无需限速。

### 术语澄清（重要，别再被字段名骗）

`downloadImage` **不返回图片字节，只返回 URL 字符串**；回调里 `cdnthumburl` / `cdnmidimgurl` / `cdnbigimgurl` **名字带 url、值却是加密 CDN fileid**（十六进制），不是可访问地址。所以「拿 URL」这一步必须调接口，省不掉。三段归属：微信给加密引用 → GeWe 换 URL（消耗账号会话，受限速）→ 百炼取字节（与我们无关）。

### 对我们架构的影响（现在只记，不实现）

- **媒体消息的 `inbox.content` 为 NULL**，源 XML 存 `media.source`。这样原始 XML **不可能**泄漏进模型提示词或 `chat_sessions`（不是靠「记得映射」，而是它根本没进 content）。文本表示由 `media` 派生（`media.render`）。详见 `architecture.md` §5.1 / §5.5。
- 会话 JSON（`chat_sessions.messages`）只写占位（`[图片]`）；`media.*` 不进会话行。
- **同一消息只取一次**：靠 `media.status` 状态机（`pending`→`ready`/`failed`/`skipped`），不复用 `new_msg_id` 唯一键。
- **生成侧 defer + 静默窗**：本会话还有 `pending` 媒体时不认领该会话（`peek_next_session` 里 `NOT EXISTS`），保证「发图求分析」一定带图；媒体**全部解析完之后再按住一个静默窗**（`MEDIA_QUIET_MS=10000`，`app/core/queue_constants.py`），把下载期间用户补发的问题收进同一批——否则图文会被拆成两轮各自回复。解除还有第二重阀门：媒体超时翻 `failed`（`media_crud.fail_stale`，在回收循环里跑）。
- **`fail_stale` 分两档（重要）**：`attempt > 0`（已发起下载未收终态）按 `MEDIA_ATTEMPT_TIMEOUT_SECONDS=30` 判卡死；`attempt = 0`（仍在排队）按 `MEDIA_QUEUE_TIMEOUT_SECONDS=420` 判排队上限。**若只按 `created_at` 绝对年龄判死，串行下载下第 6 张起就会被误杀**（30 张积压需约 200s，而超时是 30s），有效容量从 30 张被压到约 5 张，连发多图会大面积失败。
- 下载失败/跳过/超时：以「`[图片]`加载失败，无法查看」进文本，并在 Agent 人设里要求**只告知对方重发、不猜测图片内容**（防幻觉）。
- 语音要转码（silk→mp3），引入外部工具依赖；ASR 结果可落 `media.text_repr`。视频的模型侧序列化需另做（官方 `agno` 的 DashScope 不支持视频 content），参见 `decisions.md` 0013 与 rules。

## 6.5 发送文本长度（`postText`）

**GeWe 官方 `postText` 文档对 `content` 未给任何长度约束**——`send-text.md` 里该字段只写「消息内容」。所以超长行为是**微信协议层**的，且超了是报错还是静默丢弃**未知**。

微信家族有文档的限制都是**字节**口径（公众号文本 2048、企业微信文本 2048），故按字节控制：

- `WECHAT_TEXT_MAX_BYTES = 2000`（`app/utils/text_split.py`），保守值。
- **待真机实测校准**：发递增字节数的文本，看 GeWe 的 `ret`/`msg` 与对方是否真收到。这决定最终取值。
- 超限的回复由 `split_for_wechat` 按语义边界（空行 → 换行 → 句末标点 → 硬切）切成 N 段，写 N 行 outbox，**各自走原有发送与限速逻辑**。
- **代价**：N 段 = N 次 `postText`，每段吃满打字延迟上限 5s（`typing_delay_s`，≥125 字节即满）；日配额（`SEND_DAILY_CAP`）与 backlog（`OUTBOX_BACKLOG_PER_ACCOUNT`）按 N 倍消耗——一份 3 段报告占 backlog 20 中的 3。

## 7. 掉线：必须复用 appId（我们已做，补自查法）

官方对「循环掉线」的定义与自查：

> **④ 循环掉线（越登越封）**：每次掉线都重新生成二维码，账号会被微信判定为异常，越登越容易封号。
> **正确做法**：必须用上次登录的 appId 重新获取二维码登录，覆盖原有设备。
> **怎么判断是不是循环掉线**：手机微信 → 设置 → 账号与安全 → 登录过的设备；**若看到多个「iPad」设备记录，说明登录方式错了**，会一直循环掉线。

运营在 GeWe 后台重登必须复用 appId——上面这条给了**可执行的验收方法**，上线后按它自查。本服务不实现重登。

其它掉线情形（官方）：异地登录秒掉（用本地 IP，反复掉说明进入风控，次日 8 点后再试）；多设备互挤（登录时只留一个设备）。

## 8. 多账号与 Token 语义（官方 FAQ）

| 事项 | 官方口径 |
|------|----------|
| 单 Token 绑定账号数 | **无固定上限**，取决于采购授权数量 |
| 回调地址 | **单个 Token 仅支持一个回调地址**；多 Token 才能多回调、做业务隔离 |
| 到期/超额 | 部分服务到期后，「系统会**每日随机下线**超出授权数量的微信账号」 |
| SDK | 官方**不提供 SDK**，只有 HTTP API（这也是我们自写 `gewe_client` 的原因） |

**要点**：多账号若共享一个 Token，则共享一个回调地址——回调里靠 `appid` 区分节点，这对我们是可用的。到期后系统会随机下线超额账号——这是 GeWe 控制台/采购的事。本服务靠回调掉线事件和发送失败感知，**不**轮询 `checkOnline` 当健康检查。

`checkOnline`：`POST /gewe/v2/api/login/checkOnline`，`data: true/false`。可能假在线（官方与社区均提及）。**给人排障用，不进 P0 业务闭环。**
